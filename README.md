# AMS 2026 HRMS (React + Vite + Tailwind, Express + Sequelize + MySQL)

## Run
1. `CREATE DATABASE ams_hrms;`
2. `cd server && cp .env.example .env` -> set `DB_*` and `DATA_ENCRYPTION_KEY` (see the file; JWT is no longer used).
   Generate: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`
3. `npm i && npm run seed && npm run dev`  (seed wipes the DB and refuses to run when `NODE_ENV=production`; dev logins admin@ams.com / sarah@ams.com / ali@ams.com, password `Admin123!`)
4. `cd client && npm i && npm run dev` -> http://localhost:5173
5. **If you already had a database from the old version:** start the server once with `DB_SYNC_ALTER=true` (development only) so the new columns/tables are created, then remove it.
6. Tests: `cd server && npm test` (needs MySQL database `ams_hrms_test`; edit `vitest.config.ts` for your DB user/password).

## What changed in this version
**Security:** employee/attendance/leave/compliance/benefits/AI data is scoped by role (employee = self, manager = own team incl. indirect reports, HR/admin = all); approvals cannot be self-approved and managers can only act on their team; login lockout (5 fails / 15 min); terminated users are cut off on the next request; no default password (random temp password shown once); `JWT_SECRET` required; helmet, restricted CORS (`CLIENT_ORIGIN`), rate-limited login, JSON size limit, no internals leaked in errors; no automatic `sync({alter})`.
**P1** clock in/out with breaks, missing clock-out detection, own-record edits before submission, deterministic overtime engine (federal weekly + California daily/double time), timesheet submit -> manager approve/reject -> resubmit (versioned).
**P13** corrections after approval (old/new value + reason; current period vs next period depending on payroll lock/export).
**P4** payroll uses only *approved* timesheets (OT and double-time rates), subtracts active benefit deductions (P15), locks/exports with a SHA-256 file hash in the audit log, CSV-injection-safe, and moves timesheet payroll status to locked/exported.
**Bug fixed:** payroll month matching used `LIKE` on a DATE column, which Sequelize does not support reliably.

**Menu by role (2026-11-24).** The sidebar and direct URLs now follow the role: Employee sees only personal pages (dashboard, attendance, timesheets, leave, benefits, sick leave, enrollment, onboarding, credentials, training, performance, schedules, assistant); Manager adds Employees (team), compensation, offboarding, compliance, recruitment, interviews and reports; HR sees everything except Billing; Admin sees everything. A typed-in address of a page outside the role goes back to the dashboard. This is only the display layer: the server already limits every list to the person's own data (employee), the team (manager) or the company (HR / admin), and refuses the rest.

## Billing, e-mail, reports and AI assistant (2026-11-24)
**Stripe (P11/P12).** `billing.ts`: Admin-only `GET /api/billing`, `POST /api/billing/checkout` (subscription Checkout for Starter / Growth / Professional, company id in metadata, Enterprise is sales-led) and `POST /api/billing/portal` (Stripe Customer Portal: card, plan change, cancel, invoices). `POST /api/webhooks/stripe` verifies the signature over the raw body, processes each event id once and drives the state machine: checkout completed -> active (also reactivates a cancelled company); payment succeeded -> active + period end; payment failed -> past due + 7 day grace; subscription updated -> plan from the monthly amount, cancel at period end / undo; subscription deleted -> cancelled. A daily job turns an expired grace period into read-only. Billing routes stay reachable in read-only so a company can pay. New columns on Companies: `stripeCustomerId`, `stripeSubscriptionId`, `failedAt`; new table `StripeEvents`. No Stripe SDK (plain HTTPS). Env: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`.
**E-mail.** `mail.ts` + existing `mailer.ts`: company admin invitations (link also shown once), candidate messages (`POST /api/recruitment/messages/:id/send`), optional notification alerts (`NOTIFY_EMAIL=true`: title only, never the body). Every attempt is logged in `EmailLogs` (no text, no tokens, no passwords). Passwords are never e-mailed. Env: `SMTP_*`, `APP_URL`.
**Reports and exports.** `reports.ts`, `GET /api/reports` and `GET /api/reports/:key?format=json|csv|xlsx&from&to&period`. Reports: headcount, roster, attendance, leave requests, leave balances, timesheet hours, payroll, compliance tasks, audit log. Scope follows the REST rules (HR/admin company, manager team, employee none; roster / payroll / compliance HR or admin; audit admin). CSV has a UTF-8 BOM, text that starts with `= + - @` is neutralised against spreadsheet formula injection, exports are audited, 20,000 row cap, ranges of at most one year. Client page: Reports.
**AI assistant (OpenAI).** `ai.ts`, chat completions with function calling (`OPENAI_API_KEY`, `OPENAI_MODEL`, optional `OPENAI_BASE_URL`). Read tools run with the caller's permissions. Write tools (`request_leave`, `decide_leave`) only create a pending action; the same person must press Confirm in the app, within 15 minutes, once; the real leave rules (`leaveFlow.ts`, shared with the REST routes) run again at that moment. Client messages are limited to plain user / assistant text; tool results are labelled as data in the system prompt; at most 3 proposals per message and 5 model steps; 20 requests per minute per person. Prompts (first 300 chars), tool calls, proposals and decisions go to `AiAudits` (admin: `GET /api/ai/audit`) and confirmed actions also to the normal audit log. The old Anthropic integration was replaced.
**Operations.** `GET /api/health`, `TRUST_PROXY`, `DB_PORT` (was ignored before), `npm start` / `migrate:prod` / `create-superadmin:prod` for the compiled build, `TEST_DB_*` for tests plus a guard that refuses a database whose name has no "test". Migration `2026-11-24-stripe-email-ai`. **See `docs/DEPLOYMENT.md` and `docs/TEST_CHECKLIST.md`.**
**Verification run:** `tsc` clean; **338 server tests in 23 files pass** (new: `billing` 13, `ai` 15, `mail` 6, `reports` 11); client build passes; production build started with `NODE_ENV=production` on an empty database (migrate, create super admin, login cookie is HttpOnly + Secure + SameSite=Lax, webhook rejects an unsigned call, AI route needs login).

## Authentication and user management update (2026-11-23)
**Two-step verification is removed completely.** Everyone signs in with email + password only (super admin, admin, HR, manager, employee). Removed: TOTP / Google Authenticator, QR setup, recovery codes, MFA enrolment, the MFA login screens, the `/auth/mfa/*` routes, the MFA checks in session validation and in the platform console guard, the `MFA_REQUIRED_ROLES` setting, the `qrcode.react` dependency and the TOTP/recovery helpers in `platformCore.ts` (and their tests). Kept unchanged: bcrypt (cost 12) hashing, lockout (5 failed attempts / 15 min), 15 min idle and 8 h absolute session limits, CSRF header, revocation on logout / password change / termination / suspension, role checks and company data isolation.
**Roles.** `superadmin` (platform), `admin`, `hr`, `manager`, `employee`. The Super Admin role can never be created or assigned through company user management (it is not in any role list the server accepts; the create-superadmin command is the only way).
**Account creation** (`POST /api/employees`, Add Employee form, step 1 "Account"): Full name, Email, Role, Initial password, Confirm password. The creator types the initial password; it must be 12 to 72 bytes (bcrypt reads only 72), typed twice and not equal to the email; it is stored only as a bcrypt hash. Emails are unique across the platform (case-insensitive). **Admin** may create admin / HR / manager / employee. **HR** may create manager / employee only (this is stricter than before, when HR could also create HR accounts; HR can no longer create HR or Admin accounts). Manager and employee cannot create accounts. An unknown or not-allowed role is refused with 403 (before, it was silently downgraded to employee). Protected fields (status, company, lockout, the must-change flag, id) in the request body are ignored. If no password is sent, the API still generates a random one shown once (candidate hires from recruitment do the same).
**First login.** Every account created by an admin, by HR or by a recruitment hire, and every account after an admin reset, has `mustChangePassword = true`. Such a session can only reach `/auth/me`, `/auth/logout` and `/auth/change-password` (all other routes, including the platform console, answer 403 `mustChangePassword`). The client shows a "Choose a new password" screen. Changing it needs the current password, the new one must differ and meet the policy; other sessions of that user are signed out.
**Password reset.** `POST /api/employees/:id/reset-password` (admin only, body `password` + `confirmPassword`) sets a new temporary password, forces a change at next login, signs the person out everywhere, clears any lockout and writes an audit entry (never the password). It refuses your own account (use Change password), invited users (they must accept the invite), accounts of another company (404) and the platform account. Employees page: admin sees each person's role and a "Reset password" action.
**Database.** One new column, `Employees.mustChangePassword` (default 0, so every existing user keeps signing in normally). Migration `2026-11-23-remove-mfa-must-change-password` adds it and erases the stored authenticator secrets and recovery codes of everyone who had enrolled. The old `mfa*` columns and `Sessions.mfaPassed` are **not dropped** (no destructive schema change); they are no longer read or written. No users, companies or other data are touched. Upgrade: `cd server && npm run migrate`.
**Verification actually run** (MariaDB 10.11): `tsc --noEmit` clean; **292 server tests pass** (19 files; 277 before this change, including the removed MFA tests; new `tests/accounts.test.ts` has 20 tests and `tests/tenancy.test.ts` has a cross-company reset/email test); client `npm run build` (tsc + vite) passes. Covered: login without MFA for all five roles, admin creating each of the four roles with a manual password (hash checked in the database), validation (mismatch, short, over-long, bad email, duplicate, bad role), nobody can create a Super Admin, HR limits, manager/employee refused, mass-assignment ignored, forced first-login change (blocked routes, wrong current password, same password, success), forced change on admin and super admin accounts, admin reset (revokes sessions, clears lockout, forces change, audit without password), HR/manager/employee cannot reset, cross-company reset is 404, existing users unaffected, unauthenticated calls 401. **Upgrade test:** a database built by the previous version (5 users, 105 attendance rows, 9 candidates, one admin enrolled in MFA) was migrated with the new code: same row counts, MFA data erased, migration idempotent, and admin / manager / employee signed in with password only. A live HTTP run against that database confirmed create HR, first-login block, change password, admin reset and HR refused.
**Not verified.** The new screens (login, forced change, account step, reset dialog) compile and build but were not opened in a browser or checked on different screen sizes. Not deployed.

## P14 multi-tenant and sessions
**Upgrade an existing database:** `cd server && npm run migrate`. It adds `companyId` to every table, creates one **Default Company** (slug `default`) and assigns all existing rows to it. Run it before starting the new server.
**Platform owner:** `npm run create-superadmin -- owner@example.com 'a-long-password'` then sign in with that email and password. The console creates companies (name, slug, plan), invites the first admin (link shown once; email is not sent), suspends/reactivates, changes plan and subscription state.
**Tenancy:** every model except Company carries `companyId`; model hooks filter every read/count/update/delete by the request's company and stamp every insert, so a route that forgets a filter still cannot cross companies. A by-id lookup that misses inside the company but exists in another is recorded as a `cross_company_attempt` security event. Scheduled jobs run once per company. Careers pages are per company: `/careers/<slug>`.
**Sessions:** server-side, httpOnly SameSite=Lax cookie, 15 minute idle timeout, 8 hour limit, revoked on logout / password change / termination / company suspension; writes need the `X-Requested-With: ams` header (CSRF). No token in browser storage.
**Plans (P12):** every company request is checked against the company's plan and subscription state (read-only blocks writes, cancelled blocks everything). Features: credentials = Growth+, recruitment = Growth+, compensation = Professional+. Stripe is not connected yet: the platform console sets plan and subscription state by hand.
**Local development:** `npm run seed` creates company `demo` (admin@ams.com etc., password `Admin123!`).

## P4 approval and unlock, P3 rule-based compliance tasks, P2 notifications (new)
**P4 (completed):** generate from approved timesheets, **Finance review** (may adjust a sheet with a reason; the adjustment is kept as a signed line, survives regeneration and sends the sheet back for re-review), **Company Admin approval** ("Approve payroll?", or send back with a reason), **lock only after approval**, export with the file hash recorded, and **unlock with a reason** (admin only) which creates a new version and keeps the locked version in the history. Unlock is refused after export (correct in the next period, P13). Four-eyes: the approver cannot be the person who reviewed or adjusted the sheets (`PAYROLL_SINGLE_APPROVER=true` relaxes this for one-person companies); nobody reviews or approves their own pay sheet. Tax withholding is not recalculated by an adjustment: check it on the provider side. Existing databases: run `npm run migrate`. Anyone who locked payroll directly before must now review and approve first.
**P3 (completed):** task rules per company and location are compliance rules whose key starts with `task_` (task name, trigger *hire* or *annual*, due in N days, retention years); the most specific location wins (city, state, US). Tasks are created automatically (daily job or "Create tasks from rules now"), without duplicates; overdue tasks notify the owner, manager and HR once, and after 7 days overdue escalate to the Company Admin; HR can escalate manually (note required, up to level 3) or **waive with a reason** (at least 10 characters, audited, never your own task). Dashboard of open / due in 7 days / overdue by task type and location. Retention years are stored with the rule but are not yet used to set record-retention dates. Training and credential tasks come from their own modules.
**P2:** the manager is notified of a pending leave request, the employee of an automatic rejection and of the manager's decision (with the comment), and the audit log keeps the comment.

## S4 training and S5 performance, warnings, PIP (new)
**Training (S4):** HR builds a course catalogue (category, delivery method, version, optional pass mark, prerequisite, repeat every N months). HR assigns to anyone; a manager only to their own team; nobody assigns to themselves. Prerequisites must be completed first; courses with a pass mark need an assessment score (failed attempts are counted and can be retried); completion needs an acknowledgement and stores score, attempts and certificate reference; HR can record in-person completion with a verification note (never their own). Courses keep the version they were assigned. Completing a recurring course creates the next assignment automatically. Daily job: reminder 3 days before the due date, one overdue escalation to the employee, manager and HR. HR compliance dashboard per course. Managers record a competency review (approved / coaching / retraining, follow-up date required) for their own team.
**Performance (S5):** goals and expectations (versioned, measurable, employee acknowledges); evaluations (draft, then delivered, then acknowledged with an optional employee response; improvement needs factual evidence; a separate conduct note is hidden from the employee); **progressive warnings** (first written, second, final) with the five required fields, policy version and review deadline; second/final need a consistency review, and a manager-authored second/final waits for HR approval by someone other than the author; a withdrawn warning does not count on the ladder; the employee acknowledges (not agreement) or refuses with a named witness; **improvement plan** (7 to 180 days, one active, check-ins record objective progress and support, extensions capped at two); final review outcomes: success, extend, reassign/coach, or **termination review**, which is allowed only after a final warning, the final review and a documented HR/legal review, and it only **proposes** a separation (S6) that another HR user must approve. Employees see only their own delivered/issued records; managers their own team; HR everyone. Run `npm run migrate` to upgrade.

## P20/P21/S7 unemployment claims and A8 insurance register (new)
**Unemployment:** HR opens a claim for a separated employee (needs the offboarding record; one open claim per employee). The *true* separation reason (14 codes from Appendix A7) is recorded and must be explained when it differs from the separation record. The agency notice sets the employer-response deadline (10 days unless the notice says otherwise); the response needs facts, at least one piece of evidence and a confirmation of accuracy; evidence, correspondence, appeals and a restricted audit trail are kept. **The system never decides eligibility**: guidance from A7 is shown as guidance only, and HR records the AGENCY's determination from its letter (with the appeal deadline printed on it). Employer appeals after the deadline are refused. The daily job warns 2 days before a deadline and escalates a missed response once. HR/admin only.
**Insurance register:** all 15 policy types of Appendix A8 with gap view (types with no active policy), insurer, policy number, limit, premium, dates, exclusions, claims contact, covered people/assets, certificates (references, not file uploads), audited updates, renewal reminders at 90/60/30/7 days (once per threshold), automatic expiry with a compliance task, and a renewal restarts the reminders. #2 (Unemployment Insurance) is a state payroll-tax account; #12 may overlap #3 (EPLI): confirm with your broker. Run `npm run migrate` to upgrade.

## P19 part-time, P16 paid sick leave, P15 benefits (new)
**P19:** HR part-time review (average weekly hours from approved timesheets: ACA 30h flag, FMLA 12 months + 1,250 h, long-term part-time 401(k) rule); reclassify to full-time (notifies the employee, once per employee per quarter, never your own). Schedules: publish a weekly schedule, advance notice flagged where predictive-scheduling laws apply (NYC, Chicago, Seattle, San Francisco, Philadelphia, Los Angeles, Oregon; 14-day baseline: verify), every change logged.
**P16:** `Load Appendix A2 rules` seeds the 20 states + DC from the BPMN as **UNVERIFIED** versioned rules (confirm each with counsel). Accrual runs per pay period from approved timesheet hours (part-time included), respects employer-size tiers, the paid-leave size threshold (below it: company policy), annual caps and an idempotent ledger (a period can be accrued only once); year-end applies the rule's carryover (rules without a stated carryover are flagged for review). The waiting period blocks paid sick leave requests until it has passed. States with no rule use company policy.
**P15:** HR builds benefit plans from the **60 distinct benefits** of Appendix A9 (items 61-75 repeat 46-60) with employer share, hours test, waiting days and window length. Enrolling or waiving is only possible inside a window: after the waiting period, during an HR-opened open enrollment, or within 30 days of a qualifying life event (marriage, birth/adoption, loss of other coverage, reported by the employee or HR). The hours test uses the higher of scheduled hours and the rolling 13-week average actually worked, so a part-timer who works 30+ hours qualifies. Plans changed later apply to new enrollments only. Run `npm run migrate` to upgrade.

## S6 separation approval, final pay review, S8 compliance rules (new)
**Offboarding (S6):** an employee submits a resignation (reason is always *resignation*), a manager proposes a separation for their own team with a reason code; **nothing starts until HR approves**. HR can reclassify the reason on approval (audited), cannot decide their own case or one they proposed, and must give a note to stop one. The reason stays restricted (managers never see it). HR can still start an offboarding directly.
**Final pay review:** `GET /offboarding/:id/final-pay` totals unpaid approved timesheets (OT 1.5x, double time 2x), unused accrued leave (only if the state rule says it is paid out), approved bonuses and commission, and lists what HR must review. There is **no national default**: a state without a configured rule, an unverified rule, salaried staff, or unpaid bonuses/commission are flagged, and HR must explain how each was resolved before confirming (which completes the checklist task).
**Compliance rules (S8):** versioned by work state / city and effective date (`POST /api/compliance-rules`), never edited in place, with source URL, legal owner and a verified flag. Only `final_pay` rules are consumed so far. **No legal rule values are shipped: configure and verify them with counsel.** Run `npm run migrate` to upgrade.

## Employee lifecycle: P5 onboarding, P7 credentials, P8 offboarding
**Setup:** add `DATA_ENCRYPTION_KEY` (32 random bytes, base64, see `.env.example`) to `server/.env`. Without it the server starts but I-9 / W-4 submission returns 503. Back the key up: losing it makes stored I-9 / W-4 data unreadable. Existing databases: run `cd server && npm run migrate` (idempotent, recorded in `schema_migrations`). Key rotation: put the old key in `DATA_ENCRYPTION_KEY_OLD`, set the new one in `DATA_ENCRYPTION_KEY`, restart, then `POST /api/security/rotate-keys` as admin.
**P5:** creating an employee generates the onboarding checklist (I-9 S1, W-4, handbook e-sign, emergency contact, I-9 S2, W-4 verification, manager and equipment, manager acknowledgement). I-9 / W-4 are AES-256-GCM encrypted (ciphertext bound to employee and form), employees see their own data masked, only HR/admin can view decrypted data and every view is audited. Overdue tasks and late I-9 Section 2 create compliance tasks. The employee becomes Active when all mandatory tasks are done.
**P7:** credential upload, HR verification (never your own), renewal, dashboard (Compliant / Expiring soon / Expired). A job (startup + every 6 h, or `POST /api/credentials/run-reminders`) sends reminders at 90, 60, 30 and 7 days once each to employee, manager and HR, then marks the credential Expired and creates a compliance task.
**P8:** `POST /api/offboarding` replaces the old `/employees/:id/terminate`. Checklist, asset return, final pay and benefits notice with notes, retention date (cannot be shorter than the legal default), automatic access revocation on the termination date, status Terminated when everything is done. The reason is restricted to HR.

## Recruitment: P6 and S1-S3 (new)
**Upgrade:** `cd server && npm run migrate` (adds candidate columns, widens the stage list, creates 7 tables). Fresh install: `npm run seed` now includes a demo pipeline (4 jobs, 9 candidates, interviews, scorecards, a pending offer).
**Flow:** requisition (hiring manager) -> submit -> HR approves (never your own) -> HR publishes to channels -> public **/careers** page (no login) -> application intake -> structured screening -> interview -> offer -> hire, which creates the employee and starts P5 onboarding.
- **Careers page** `/careers`, `/careers/:id`: search, pay range, apply form with consent, neutral work-authorization questions, honeypot and rate limit, duplicate detection per job, "applied before" flag across jobs.
- **Guardrails (S8):** screening questions are checked against restricted topics (age, religion, family, health, citizenship, salary history); pay range is mandatory to publish in pay transparency states (A4); the same weighted rubric for every applicant; a work-history discrepancy cannot lead to rejection until the candidate's clarification is recorded; rejection needs a reason code.
- **Interviews (S3):** panel scheduling with invitation template and accommodation contact; scorecards are **blind** (a panelist cannot see colleagues' scores until they submit their own); an offer needs at least one scorecard and not a unanimous "no"; the hiring manager approves the candidate.
- **Offers:** maker-checker (HR drafts, hiring manager or another HR approves), checked against the posted pay range and the exempt salary floor (P17), response deadline, acceptance creates the employee, leave balances, manager link and onboarding checklist. Requisition becomes Filled when openings are met.
- **Background checks (S2):** FCRA order enforced: disclosure, signed authorization, report, pre-adverse notice, 5 business day wait, final adverse notice (auto-rejects with the right reason).
- **Candidate emails:** written from approved templates into an **Outbox**. With SMTP configured, "Send email" delivers it; without SMTP copy it out and "Mark sent".
- **Roles:** employees only see **My Interviews** (their panels and scorecards); managers see their own jobs and candidates; HR sees everything.

## Compensation (P9, P10, P17, P18) and resume upload (new)
**Upgrade:** `cd server && npm run migrate` (adds `commission` / `bonus` to PaySheets and creates 5 tables). Fresh install: `npm run seed`.
**Commission (P9):** HR assigns a flat or tiered plan (cap, recoverable draw) -> sales are recorded by the employee, their manager or HR (active plan, no future dates, locked months refused) -> HR calculates the month -> manager or HR approves or returns (never your own) -> approved lines feed payroll. A refund recorded by HR becomes a negative line at the next calculation.
**Combined pay (P10):** payroll adds approved commission and approved bonuses on separate columns (`commission`, `bonus`, also in the CSV), and non-exempt staff get the extra overtime premium on commission and non-discretionary bonuses.
**Bonuses (P18):** manager or HR proposes (not for yourself) -> a different HR user approves -> 22% / 37% supplemental withholding is stored -> payroll lock marks it paid -> HR can record a clawback only with a signed agreement, inside the window; if the state limits wage deductions it is collected by invoice instead of payroll deduction.
**Pay changes (P17):** proposed with the exempt salary floor check (federal or state, whichever is higher) and an optional pay band -> a different HR user approves after confirming the budget -> applied from the effective date (automatically before payroll or when the list opens). Old pay is kept on the record.
**Resume upload:** applicants upload PDF / DOC / DOCX up to 5 MB on the careers page or the recruiter form. The server checks the real file bytes and stores the file under a random name in `UPLOAD_DIR` (default `server/uploads/resumes`); staff download it from the candidate page (scope rules apply, every download is audited).
**Verification status:** the rules in `payCore.ts` and `resumeCore.ts` have unit tests that were run. The routes, payroll integration, migration and screens were only checked for syntax: they have **not** been compiled against the real dependencies, run against a database or covered by API tests. Run `npm run build`, `npm run migrate` and `npm test`, then the manual checks below before relying on them.
**Manual checks:** (1) assign a plan, record two sales, calculate, approve, generate and lock payroll, confirm commission appears on the sheet and CSV; (2) refund a sale and recalculate next month; (3) propose and approve a bonus as two different HR users; (4) propose an exempt salary under the CA floor (must be refused); (5) upload a PDF and a renamed .exe on the careers page (the .exe must be refused).

## Known limits
Stripe, SMTP and OpenAI were exercised only with simulated providers (tests) and must be proven with real test accounts (`docs/TEST_CHECKLIST.md`, sections 7, 8, 10). Overtime rules exist for federal + CA only. Tested on MariaDB 10.11, not MySQL 8. The UI was type-checked and built but not visually tested on different screen sizes.
